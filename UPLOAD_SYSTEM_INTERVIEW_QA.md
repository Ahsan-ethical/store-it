# StoreIt Upload & Sharing System — Interview Q&A

A trace of how file upload, caching, download, encryption, decryption, pause/resume, and share-link revocation actually work in this codebase, written as interview-style Q&A. The emphasis throughout is *why* — the constraint or incident behind each decision, not just what the code does. Every answer is grounded in the real implementation (file paths and function names included) rather than generic textbook explanations.

---

## Concurrent Requests

### Q: Walk me through what happens, concurrency-wise, when a large file is uploaded.

A large file (over the 10MB S3 direct-upload threshold) goes through `POST /api/files/telegram/init`, which splits it into fixed-size chunks (4-10MB depending on the path) and returns a `totalChunks` count. The client then spins up a **fixed-size worker pool** — `hooks/useUpload.ts`'s `uploadChunks()` and `client/lib/telegramWorker.ts`'s `resumeTelegramUpload()` both use `CHUNK_CONCURRENCY = 6` — rather than firing `totalChunks` requests all at once. Each worker is an async loop that atomically claims the next chunk index from a shared counter (`nextIndex.current++` / `lock.current++`) and uploads it; `Math.min(CHUNK_CONCURRENCY, totalChunks)` workers run via `Promise.all`, so a 3-chunk file gets 3 workers and a 300-chunk file still only ever has 6 in flight at once.

### Q: Why a bounded worker pool instead of just `Promise.all`-ing every chunk at once?

Because chunk count scales with file size with no upper bound — a `Promise.all` over every chunk would mean a 2GB file spawns hundreds of simultaneous requests, hammering both this server's own concurrency limits and Telegram's per-chat rate limit (chunks are relayed as Telegram messages to one channel). A worker pool caps concurrency at a constant regardless of file size, so throughput scales but load doesn't.

### Q: Why 6, specifically?

Not derived from a formula — it's an empirically-carried-over number. `client/lib/telegramWorker.ts`'s refresh-survival resume path already used 6 concurrent workers successfully; when the *live* upload path in `hooks/useUpload.ts` was found to be strictly sequential (a real perf bug — see the next answer), it was unified to match the already-proven number rather than tune a new one from scratch. The actual justification for "why not 1" is more concrete than "why 6 and not 8": per-chunk timing logs (`[telegram/chunk timing] ... accessChecks=...ms readAndEncrypt=...ms sendDocument=...ms dbWrite=...ms`, added in `app/api/files/telegram/chunk/route.ts` specifically to answer this) show the dominant cost is `sendDocument` — the server's round trip to Telegram's API — which is mostly the *server* waiting on a third party, not CPU work on either end. Sequential chunks meant the client sat idle waiting on that same dead time chunk after chunk; overlapping several chunks lets that dead time overlap instead of stack.

### Q: What stops a slow or failing chunk from blocking the other 5 workers?

Nothing does, by design, at the worker level — each worker's `while` loop only cares about its *own* current chunk; a slow chunk in worker 3 doesn't block workers 1, 2, 4, 5, 6 from continuing to claim and send other indices. Retries are also scoped per-chunk, not global: `uploadOneChunk`'s own loop retries a failed chunk up to 3 times with exponential backoff (1s, 2s, 4s) *within that one worker*, so one bad chunk degrades that worker's throughput, not the whole batch's.

### Q: There's retry logic in both the client (`uploadOneChunk`) and the server (`app/api/files/telegram/chunk/route.ts`'s own `MAX_RETRIES = 3` loop). Isn't that redundant?

They cover different failure domains, not the same one twice. The server's retry loop specifically targets Telegram's own `429` flood-control response — it reads Telegram's suggested `retry_after` and sleeps that long (capped at `MAX_RETRY_AFTER_MS = 8000` — deliberately never blocking a single server invocation past that, even if Telegram asks for longer, since the route almost certainly runs under an execution-time budget; better to fail fast and let the client fall back to S3 than eat the whole budget sleeping). The client's retry loop is one layer up: it retries the *entire* HTTP request-response cycle for any failure — a dropped connection, a timeout, a non-429 5xx — cases the server-side retry never even sees because the request never made it there cleanly, or where the server already exhausted its own retries and returned a final failure.

### Q: How does resuming an upload avoid re-sending chunks that already succeeded?

Two independent layers, not one. Client-side: before resuming, the client calls `GET /api/files/telegram/{fileId}/resume`, which returns `uploadedIndexes` — every chunk index already recorded in the `TelegramChunk` collection for this file — and workers skip any index in that set (`if (existingUploadedIndexes.has(i)) continue;`). Server-side, independently: `app/api/files/telegram/chunk/route.ts` checks `TelegramChunk.findOne({fileId, chunkIndex})` *before* doing any work, and short-circuits with "Chunk already uploaded" if a record exists — so even if the client's snapshot is stale (a chunk finished after the client fetched `/resume` but before it started this pass), the server won't double-record it. And if two requests for the *same* chunk index somehow race past that check simultaneously (exactly what the pause/resume bug below produced), a unique index on `(fileId, chunkIndex)` in `TelegramChunk` makes the loser's `create()` fail with a Mongo duplicate-key error (`11000`) — which the route catches, deletes the Telegram message it had just (wastefully but harmlessly) sent, and returns success anyway. Concurrency safety here is defense in depth: client-side dedup is an optimization to avoid wasted work; the server-side unique constraint is what actually guarantees correctness if that optimization fails.

### Q: Speaking of that — what did fail, concretely, in the pause/resume bug this session?

That dual idempotency is exactly what kept the bug from corrupting data, but it didn't stop it from *happening*. See the Pause/Resume section below for the full root cause; the short version relevant here is that it was a pure concurrency bug — two independent worker batches (one that should have stopped, one freshly started) both believed they owned the "next chunk to send" counter and neither knew about the other, so they raced on overlapping indices. The `TelegramChunk` unique index turned what could have been silent duplicate records into harmless, self-cleaning collisions instead — but the *wasted* concurrent load (2-3x the intended 6 workers, all hitting the same Telegram chat) is the direct explanation for chunk sends that were measured taking 10-100+ seconds in production logs, versus the single-digit seconds a lone 6-worker batch normally sees.

### Q: If you had to scale this to many more concurrent users, what would you change?

The worker pool is entirely client-driven — there's no server-side job queue, just bounded concurrent HTTP requests per browser tab. That's a reasonable shape for a single user uploading their own files, but it means server-side load is really "however many browser tabs happen to be uploading right now × 6," with no global admission control. At real scale I'd put a queue (e.g. BullMQ backed by Redis) between the API and the Telegram-send step, so the server — not each client independently — controls total concurrent Telegram API load across *all* users, and chunk workers become queue consumers instead of direct callers. I'd also revisit the `useResume` hook's single shared `pauseRef`/`cancelRef`/`abortRef` (not per-file) — today, resuming two different pending files at once would have them stomp on each other's control refs; that's a known, separate gap from the pause/resume race fixed this session, not yet fixed itself.

## Caching Logic

### Q: How many distinct caching layers actually exist in this file pipeline, and what does each one hold?

There are four, each with a different scope and a different reason to exist, not one general-purpose cache reused everywhere:

1. **`client/lib/previewCache.ts`** — IndexedDB (`StoreItPreviewCache`), client-side, stores the fully **decrypted** `Blob` for a zero-knowledge file after it's been fetched-and-decrypted once, keyed by `${fileId}:${versionId}`.
2. **`server/lib/telegramChunkCache.ts`** — S3-backed, server-side, stores raw **chunk bytes exactly as Telegram returned them** (ciphertext for encrypted files, plaintext for unencrypted ones), keyed by `telegram-cache/${versionId}/${chunkIndex}`. This sits in front of Telegram itself and is shared by every request from every device/user hitting that version's chunks — not per-browser.
3. **`client/lib/dekStore.ts`** — IndexedDB (`StoreItKeys`), client-side, caches the account's raw **DEK bytes** so a returning user on the same browser doesn't have to re-enter their recovery code every session. This is caching a *key*, not content.
4. HTTP-level: both `app/api/files/[id]/manifest/route.ts` and `app/api/files/[id]/chunk-data/[index]/route.ts` set `Cache-Control: private, max-age=86400, immutable` — a plain browser-cache layer sitting in front of all of the above, valid because a manifest/chunk for a given `versionId` never changes once uploaded (a new version gets a new `versionId`).

The interesting design point: layers 1 and 2 cache *different things* (plaintext vs ciphertext) at *different scopes* (one browser vs. globally) for *different reasons* (avoid re-decrypting AES-GCM client-side vs. avoid re-hitting Telegram's slower, rate-limited API). Neither can replace the other — the server-side cache can't hold plaintext because for `encryptionMode: 'dek'` files the server never has the key at all.

### Q: Why is the decrypted preview blob cached client-side in IndexedDB instead of just re-decrypting on every open, or caching it server-side?

Re-decrypting on every open means re-fetching every chunk over the network (`GET /api/files/[id]/chunk-data/[index]`) and re-running AES-GCM on all of them (see `client/lib/decryptedDownload.ts`'s `fetchAndDecryptFile`) — for a large file, that's real, repeated cost just to reopen a preview you already paid for once. Caching it server-side isn't an option for the reason the whole feature exists: for `encryptionMode: 'dek'` files, the DEK is deliberately never sent to or held by the server (zero-knowledge design — see `server/services/fileService.ts`'s `getFileChunkData`, which explicitly never decrypts, "since for 'dek'-mode files the server never has the key"). The only place that ever legitimately holds plaintext is the browser that unwrapped the DEK, so that's the only place a plaintext cache can live.

### Q: Why key the preview cache by `(fileId, versionId)` instead of just `fileId`?

Because `fileId` is stable across the file's whole lifetime but its *content* isn't — uploading a new version keeps the same `fileId` but gets a new `versionId` (`server/services/versioningService.ts`, part of the file-versioning refactor). If the cache were keyed by `fileId` alone, reopening a file after uploading a new version would silently serve the stale, previous version's decrypted bytes from cache. Keying by the pair means a new version is automatically a cache miss — there's no explicit invalidation logic needed at all, it just falls out of the key shape. The same reasoning is why `manifest`'s and `chunk-data`'s HTTP `Cache-Control: immutable` headers are safe: `(versionId, chunkIndex)` content genuinely never changes once written, so "immutable" is actually true, not just optimistic.

### Q: What happens if the preview cache is stale, corrupted, or IndexedDB just isn't available (private browsing, quota exceeded, storage disabled)?

It degrades to exactly the non-cached path, never a broken file. `getCachedPreviewBlob` wraps everything in a try/catch and returns `undefined` on any failure — the comment states the intent directly: "Cache is a pure optimization — any IndexedDB failure... just means falling back to a live fetch, never a broken preview." Same for writes: `storeCachedPreviewBlob` swallows failures (e.g. quota exceeded on a large file) and just accepts that the next open re-pays the live-fetch cost. "Staleness" for wrong content isn't really reachable given the `(fileId, versionId)` keying above — the closest thing to it is a genuinely orphaned entry (old version's blob sitting around after a new version was uploaded), which is why there's also a 24-hour TTL sweep (`cleanupOldRecords`, run once per page load via a `cleanupRan` module-level flag) — not for correctness, just to bound how much space these accumulate.

### Q: Why does the DEK cache (`dekStore.ts`) live in a completely separate IndexedDB database (`StoreItKeys`) instead of being another object store inside `StoreItPreviewCache` or the upload-resume database?

The comment in the file states it plainly: "different lifecycle, different sensitivity, no reason to share a version number with unrelated features." Concretely: `StoreItKeys` has no TTL and no cleanup sweep at all — a DEK cache entry is meant to persist indefinitely until explicit logout/removal, whereas the preview cache and upload-resume stores both have a 24-hour TTL sweep tied to bulk, disposable data. More importantly, IndexedDB's `onupgradeneeded` runs against the whole database when *any* store's version bumps — bundling a security-sensitive key store into the same database as upload scratch data means every future schema change to the upload/preview logic (bumping `DB_VERSION`) would run its upgrade transaction against the key store too, for no reason. Isolating it removes that coupling entirely — a schema change to how uploads are cached can never accidentally touch key storage.

### Q: `client/lib/indexedDB.ts` and `client/lib/uploadQueueDB.ts` actually share one physical database (`StoreItResume`, same `DB_NAME`/`DB_VERSION`) but use two different object stores (`files` vs `uploadQueue`). Why split into two stores instead of one, if they're in the same DB anyway?

Because they serve two different access patterns, not just two different pieces of data. `uploadQueueDB`'s `uploadQueue` store is *enumerated wholesale* — `hooks/useUpload.ts`'s `restoreQueue()` calls `getAllQueueItems()` (an `openCursor()` walk over every record) on mount to rebuild the entire "Uploads" card from whatever was in flight before a refresh; it's keyed by the *client-generated* `upload_<timestamp>_<counter>` id since a page reload happens before the server necessarily even knows about a fresh upload yet. `indexedDB.ts`'s `files` store, by contrast, is a *point lookup* — `hooks/useResume.ts`'s `startResume()` already knows the server `fileId` (from `/api/dashboard`'s `pendingFiles`) and just needs `getFile(fileId)` to fetch back the one blob/handle it needs. Genuinely different query shapes, so genuinely different stores makes sense even sharing one database.

That said, sharing the physical database is a real, callable-out cost: both files' comments explicitly flag that `DB_VERSION` must be manually kept in sync between them, and whichever module's `openDB()` runs first is the one whose `onupgradeneeded` actually creates *both* stores — an invariant enforced only by comment discipline, not by the type system or a shared constant. That's a legitimate "how would you improve this" answer: pull `DB_NAME`/`DB_VERSION`/the upgrade handler into one small shared module both files import, so there's a single source of truth instead of two files independently promising to agree.

### Q: `hooks/useResume.ts`'s `startResume()` checks an in-memory `Map` (`resumeHandleCache`/`resumeFileCache` in `client/lib/resumeCache.ts`) before falling back to the IndexedDB lookup. Why cache the same thing twice, in two different places?

It's a cost-ordered cascade, not redundant duplication — cheapest and fastest check first, most disruptive last: in-memory `Map.get()` (synchronous, ~free) → IndexedDB `getFile()` (async, a real I/O round-trip, but silent to the user) → prompting the user to re-pick the file via `showOpenFilePicker()`/a file input (the only option left, and it interrupts them). The in-memory cache only helps *within the same page load* (e.g. you paused and resumed the same file twice without navigating away) and is trivially lost on any refresh — which is exactly why the IndexedDB layer exists underneath it, per the comment: "survives a page refresh, unlike the in-memory caches above." Each layer exists to cover a gap the one below leaves.

### Q: Is it actually safe that decrypted file content ends up sitting in IndexedDB as plaintext, given the entire point of DEK/zero-knowledge encryption is that content shouldn't be readable without the right key?

This is worth being precise about rather than just waving it away. It doesn't weaken the *server-side* threat model at all — IndexedDB is browser-local storage that never leaves the device, so the server still never sees plaintext, which is the property zero-knowledge encryption actually promises. But it does modestly widen the *client-side* exposure window: without the preview cache, decrypting a file requires the DEK to be live in memory for that session (unwrapped either from `dekStore.ts`'s per-device cache or freshly via a recovery code) — nothing readable persists once the tab closes. With the preview cache, a decrypted blob *does* persist across sessions (bounded by the 24h TTL) without needing the DEK again at all. So anyone with access to that browser profile/device within that 24-hour window — a shared computer, a stolen unlocked laptop, another process reading the same origin's IndexedDB — gets previously-opened files' plaintext for free, whereas today they'd at minimum need the device's cached DEK too. It's a real, if bounded and arguably reasonable, trade-off (convenience vs. a strictly larger blast radius on device compromise), and it's the kind of thing worth flagging explicitly rather than asserting "it's fine" outright.

### Q: You mentioned `uploadQueueDB.ts`'s cleanup doesn't have the same `.catch()` its sibling files do — is that a real bug?

Yes, a small but real one. `client/lib/indexedDB.ts` and `client/lib/previewCache.ts` both call `cleanupOldRecords(db).catch(() => {})` on open, but `client/lib/uploadQueueDB.ts` calls `cleanupOldRecords(db)` with no `.catch()` at all. `cleanupOldRecords` there does return a value from an `onsuccess` handler but the function itself is `async` and can reject (e.g. a transaction error on `openCursor()`), and nothing observes that rejection — an unhandled promise rejection, silently swallowed by the runtime rather than explicitly swallowed by the code. It's low-severity (this is best-effort space-reclamation, not correctness-critical), but it's exactly the kind of copy-paste-drift bug you'd expect from three near-identical files maintaining the same "swallow cleanup errors" convention independently instead of sharing one implementation.

## Download Flow

### Q: Walk me through what happens end-to-end when a user clicks "download" on a file.

It starts in `hooks/useFiles.ts`'s `downloadFile(file)`. If `file.backend !== "telegram"`, there's nothing to decrypt client-side, so it goes straight to `GET /api/files/[id]/download`, which (per `server/services/fileService.ts`'s `getFileDownload`) is either a plain **302 redirect** to a presigned S3 URL (native S3 file) or, for a Telegram-backed file using the *old* server-held-key encryption mode, a **server-streamed** response (`createTelegramDownloadStream` in `server/lib/download.ts`) that decrypts chunk-by-chunk as it streams. If `file.backend === "telegram"` *and* the file needs client-side decryption, `resolveDecryptedBlobUrl` runs first: fetch the manifest (`GET /api/files/[id]/manifest`), check the local preview cache, and if it's a miss, fetch every ciphertext chunk (`GET /api/files/[id]/chunk-data/[index]`) with 4-way bounded concurrency and decrypt each with the session DEK (`client/lib/decryptedDownload.ts`'s `fetchAndDecryptFile`), then assemble a `Blob`, cache it, and hand back an object URL that gets clicked programmatically via a hidden `<a>` tag.

### Q: How does the server decide whether a file is served via redirect, server-side stream, or client-side manifest+chunks?

Three independent booleans, checked in this order of precedence: **backend** (`s3` vs `telegram`) and **encryption mode** (`file.encryptionMode === 'dek'` vs. server-held `encryptionKey` vs. none). `getFileDownload` only distinguishes backend — S3 file → redirect; Telegram file → stream (decrypting server-side only if a legacy `encryptionKey` exists, otherwise passing bytes through as-is). `getFileManifest` is the one that actually checks encryption mode: `requiresClientDecrypt = version?.backend === "telegram" && file.encryptionMode === "dek"` — that's the single line that decides whether the client needs to go down the manifest+chunks path at all. Notably, `hooks/useFiles.ts`'s `openFile`/`downloadFile` don't even bother calling the manifest endpoint for non-Telegram files — since `requiresClientDecrypt` can only ever be true when `backend === "telegram"`, checking `file.backend` client-side first is a free short-circuit that skips a network round-trip for the common (S3) case.

### Q: Why can't a zero-knowledge (`dek`-mode) file just be served the same way an S3 file is — a redirect to a URL?

Because a redirect only works when the *server* can hand back something directly usable — a presigned S3 URL pointing at already-plaintext (or server-decryptable) bytes. For `dek`-mode files, the server holds only ciphertext and never the key (that's the entire point of zero-knowledge encryption — see `getFileChunkData`'s comment: "never decrypted server-side, since for 'dek'-mode files the server never has the key"). There is no URL the server could generate that resolves to plaintext, because the server literally cannot produce plaintext. The only entity that can ever decrypt the content is whichever browser has unwrapped the DEK, so decryption is structurally forced to happen client-side — hence the manifest (list of chunks + their nonces) plus a raw-ciphertext-chunk endpoint, instead of a single download URL.

### Q: There's a server-side S3-backed cache (`telegramChunkCache.ts`) sitting between the Telegram fetch and both the streaming download route *and* the client's chunk-data route. Why cache Telegram chunks at all, and why in S3 rather than in-memory or in the database?

Telegram's Bot API is the slow, rate-limited part of this whole pipeline (this session's earlier concurrency work traced `sendDocument` calls taking anywhere from single-digit to 100+ seconds under load) — every repeat view of the same file/chunk would otherwise re-pay two live network hops to Telegram (fetch the file path, then fetch the bytes) for content that, per-version, never changes. Caching in S3 rather than in-memory means the cache survives server restarts/multiple instances and can reuse the exact same presigned-URL/CDN delivery path already built for native S3 files — a comment in the file makes this explicit: it's what "lets it ride the same presigned-URL/CDN path already used for native S3 files." Telegram remains the authoritative source; the cache is described as "always regenerable from it, so losing it is never a correctness problem" — a pure performance layer, not a durability guarantee.

### Q: Is it safe for that server-side chunk cache to store the same bytes regardless of whether the file is encrypted?

Yes, deliberately — it stores **exactly what Telegram returns**, meaning ciphertext for encrypted files and plaintext only for files that were never encrypted at all; it never decrypts anything itself. The file's own comment draws the direct parallel: "Caching ciphertext is safe regardless of who can reach this S3 key: it's meaningless without the file's key, same reasoning already applied to dek-mode chunks served directly to clients for local decryption." In other words, this cache's security posture rides entirely on the *same* file's actual encryption status — it doesn't introduce a new exposure, it just stores a byte-for-byte copy of something that's either already safe to store as-is (already encrypted) or was never protected to begin with (legacy unencrypted files).

### Q: What happens if the client's chunk fetch fails partway through decrypting a large file — a network blip on chunk 7 of 20, say?

`fetchAndDecryptFile`'s worker pool (`client/lib/decryptedDownload.ts`) has no per-chunk retry logic at all — a single failed `fetch` (`if (!res.ok) throw ...`) propagates straight up through `Promise.all`, rejecting the whole `fetchAndDecryptFile` call. `hooks/useFiles.ts`'s `resolveDecryptedBlobUrl`/`openFile`/`downloadFile` catch that at the top level and just show a generic "Failed to open file" / "Download failed" toast — there's no partial-progress save, no resume-from-chunk-7, no automatic retry. That's a real, notable gap compared to the *upload* path, which has three layers of retry/backoff/resume built in (`app/api/files/telegram/chunk/route.ts`'s exponential backoff, plus this session's whole pause/resume drain fix) — the download-and-decrypt path has none of that sophistication. If asked "how would you improve this," per-chunk retry with backoff (mirroring the upload chunk route's `MAX_RETRIES`/`RETRY_DELAYS` pattern) would be the direct answer, since the chunk-data endpoint is already cached and idempotent — retrying a failed chunk fetch is safe and cheap.

## Encryption

### Q: Walk me through what happens end-to-end when a user uploads a large file that gets encrypted.

Two independent things determine the path: which storage backend the file lands on (S3 for anything ≤10MB, Telegram for anything larger — see `SMALL_FILE_LIMIT` in `hooks/useUpload.ts`), and which encryption mode the account uses. For a large file with an unlocked zero-knowledge DEK (`getSessionDEK()` returns non-null), `hooks/useUpload.ts`'s `uploadOneChunk` does the encryption **client-side, per chunk, before the network call**: it slices the file into `chunkSize` pieces (chunk size comes back from `/api/files/telegram/init`), calls `encryptChunk(chunkBuf, cryptoKey)` from `hooks/useFileEncryption.ts` — which generates a fresh random 12-byte nonce and runs AES-GCM — then computes a SHA-256 hash of the **ciphertext**, and uploads `{fileId, chunkIndex, hash, chunk: ciphertextBlob, nonce, useEncryption: "false"}` as multipart form data. Server-side, `app/api/files/telegram/chunk/route.ts` sees `file.encryptionKey` is unset (zero-knowledge mode) and takes the `else` branch: `dataToStore = chunkBuffer` (the ciphertext, unchanged), `chunkNonce = nonce`, `storedHash = hash` — it never touches plaintext, never sees the DEK, just forwards already-encrypted bytes to Telegram via `sendDocument` and records `{fileId, chunkIndex, hash, plaintextHash, nonce, telegramMessageId, telegramFileId}` in the `TelegramChunk` collection. If no DEK is unlocked on this device, the client instead sends the **plaintext** chunk with `useEncryption: "true"`, and the server falls into the `if (file.encryptionKey)` branch — generates/uses a per-file key, encrypts server-side with `encryptChunkWithNonce`, and stores the resulting ciphertext. Either way, what ends up on Telegram's servers is ciphertext; the difference is *where* the encryption happened and *who holds the key*.

### Q: Why AES-GCM specifically, and not something like AES-CBC?

Every encrypt/decrypt call in this codebase — client-side (`hooks/useFileEncryption.ts`'s `encryptChunk`/`decryptChunk`, Web Crypto `crypto.subtle`) and server-side (`server/services/encryptionService.ts`, Node's `crypto.createCipheriv("aes-256-gcm", ...)`) — uses AES-256-GCM, an **authenticated** encryption mode (AEAD). CBC only gives you confidentiality: it'll happily decrypt a bit-flipped or truncated ciphertext into different-but-plausible-looking garbage, and you need a separate MAC (HMAC-then-encrypt or similar) bolted on to catch tampering — a construction that's easy to get subtly wrong (padding-oracle-style attacks have come from exactly that kind of DIY composition). GCM produces a 16-byte authentication tag (`AUTH_TAG_SIZE = 16` in both files) alongside the ciphertext; `crypto.subtle.decrypt`/`decipher.final()` **throws** if that tag doesn't verify, so a tampered or corrupted chunk fails loudly at decrypt time instead of silently returning wrong bytes. For a system storing encrypted file chunks pulled back from a third-party (Telegram) over the network, "detect tampering/corruption automatically, for free, as part of decryption" is exactly the property you want, and GCM gets you there without hand-rolling a MAC.

### Q: Why PBKDF2 with 600,000 iterations for the recovery-code-derived wrapping key, and why is the DEK itself just random bytes rather than derived from anything?

These solve two different problems, which is why they use two different approaches. The DEK (`generateDEKBytes()` in `client/lib/dek.ts`) is 32 bytes from `crypto.getRandomValues` — it has nothing to do with anything the user knows or remembers, so there's no reason to derive it; you want maximum entropy (256 bits) with zero structure an attacker could exploit, and a CSPRNG gives you exactly that. The **wrapping key** (used only to encrypt the DEK for storage, so it can survive a login-on-a-new-device) is different: it's derived from the recovery code, which is high-entropy (160 bits from `generateRecoveryCode()`) but still something a human is meant to *hold and re-type*, so brute-forcing it isn't purely an information-theoretic question — it's about making each guess expensive. `deriveKey()` uses PBKDF2-HMAC-SHA256 with 600,000 iterations specifically to slow down an attacker who somehow got hold of the wrapped blob + salt (`encryptionRecoveryWrapped`/`encryptionRecoverySalt`, stored server-side) and is trying to brute-force the code offline — each guess now costs a deliberately non-trivial amount of CPU time instead of a single hash operation. Given the recovery code already has 160 bits of entropy, PBKDF2's job here is defense-in-depth against a weaker-than-expected code, not the primary line of defense — but it's the standard, correct thing to do whenever you're deriving a key from something a human transcribes.

### Q: Why does this codebase support two different encryption modes — a per-file server-held key *and* an account-wide zero-knowledge DEK — instead of just picking one?

They exist because they solve different problems, and the DEK mode came later without ripping out the older one (you can see this directly in `app/api/files/telegram/chunk/route.ts`'s comment: `// Backward compat: if file has server-side encryptionKey, encrypt on server (old method)`). The **server-managed mode** (`EncryptionKey` model — one document per file, `keyBase64` stored server-side) means the server *can* decrypt on the user's behalf: it enables server-side features like generating thumbnails, or (in principle) serving a preview without the client needing to do any crypto — at the cost of the server being a single point of trust; anyone with DB + application access can read every file. The **zero-knowledge DEK mode** (`file.encryptionMode === "dek"`) inverts that: the server never sees the key at all, so even a full database compromise doesn't expose file contents — but it also means the server *cannot* do anything with the plaintext, decryption only ever happens client-side (see `server/services/fileService.ts`'s `requiresClientDecrypt` gate), and a user who loses both their device's cached DEK *and* their recovery code loses that data permanently — there's no support "reset my password and get my files back" path for DEK-mode content, by design. Supporting both lets the product default new accounts into the strictly-better zero-knowledge mode going forward while not having to migrate or break every file already encrypted under the older per-file-key scheme.

### Q: The comment in `hooks/useUpload.ts` mentions the DEK replaced "the old per-file passphrase-derived key" — what problem did that solve, and what new problem did it introduce?

A per-file, passphrase-derived key means every single file needs its own salt and its own PBKDF2 derivation before you can touch it — resuming an interrupted upload, or opening a file on a second device, means re-deriving (or re-fetching/re-deriving) a *different* key each time, and the UX has to ask for or remember a passphrase at a much finer granularity. The account-wide DEK collapses that: unlock once per device (via the cached copy in `client/lib/dekStore.ts`'s IndexedDB store, or once via the recovery code), and every file the account owns just works — that's explicitly why `resumeSingleUpload` can "just re-read it fresh" instead of doing any per-file key setup. The new problem that introduces is blast radius: with one key per file, compromising a single file's key exposes *that file*. With one DEK for the whole account, compromising that one key — or the recovery code that unwraps it — exposes **every file the account has ever encrypted**, past and future, in one shot. The design accepts that trade deliberately: it's the same trade every "single master key" scheme makes (a password manager's master password is the same shape of risk), justified by how much simpler and more usable it makes cross-device, cross-file access.

## Decryption

### Q: Walk me through downloading and decrypting a Telegram-backed, DEK-encrypted file.

The client first calls `fetchManifest(fileId)` (`client/lib/decryptedDownload.ts`), hitting `/api/files/[id]/manifest`, which — per `server/services/fileService.ts` — only returns `requiresClientDecrypt: true` plus real chunk data (`{index, nonce, size}` for every chunk, sorted by `chunkIndex`, scoped to a specific `versionId`) when `version.backend === "telegram" && file.encryptionMode === "dek"`; anything else gets `requiresClientDecrypt: false` and downloads through the normal (already-decrypted-server-side-or-never-encrypted) path. If the manifest says client decryption is needed, `hooks/useFiles.ts`'s `resolveDecryptedBlobUrl` calls `fetchAndDecryptFile(fileId, manifest, dek)`, which spins up a small worker pool (`CONCURRENCY = 4`) that, for each chunk, hits `/api/files/[id]/chunk-data/[index]?versionId=...` to pull the raw ciphertext bytes (the server here does zero decryption — it just streams whatever's cached or re-fetches from Telegram via `getFile`/`getFileDownloadUrl`, gated behind `getAuthUser()` + `getFileChunkData`'s ownership check), then calls `decryptChunk(ciphertext, dek, nonce)` — using the **exact nonce that was stored alongside that chunk at upload time**, fetched from the manifest, not regenerated. Once every chunk's plaintext is in its correct array slot (`parts[i] = plaintext`, indexed by position so out-of-order completions from the concurrent workers still land correctly), they're concatenated directly into one `Blob` and handed back to the caller for preview/download.

### Q: The chunks are fetched concurrently and can finish out of order — how does the code guarantee they're reassembled in the right order?

`parts` is pre-sized as `new Array(chunks.length)`, and each worker writes to `parts[i]` using the chunk's own index (`const i = nextIndex++` claims a slot, and `parts[i] = plaintext` writes to that exact position) rather than pushing onto a running array. So even though 4 workers are racing to fetch-and-decrypt different chunks, and worker completion order has nothing to do with chunk order, the final `new Blob(parts, ...)` always sees a fully-populated, correctly-ordered array once `Promise.all` resolves — the ordering guarantee comes from indexed writes, not from anything about *when* each chunk finishes.

### Q: What actually stops a corrupted or tampered chunk from being silently reassembled into a broken file?

AES-GCM's authentication tag, and it fails at exactly the right layer: `decryptChunk` (both the client `hooks/useFileEncryption.ts` version and the server `server/services/encryptionService.ts` version) calls the underlying platform's authenticated decrypt (`crypto.subtle.decrypt` / `decipher.final()` after `setAuthTag`), which throws if the tag doesn't verify against the ciphertext+nonce+key. Any single flipped bit in transit or at rest — Telegram serving corrupted bytes, a bug elsewhere writing the wrong nonce, someone tampering with the stored ciphertext — causes that specific chunk's decrypt call to throw, not to quietly produce different bytes. Since `fetchAndDecryptFile`'s workers `await decryptChunk(...)` directly with no try/catch swallowing the error, that exception propagates straight out of `Promise.all`, and the whole file-open attempt fails loudly instead of silently handing the user a corrupted file. There's a separate `hash`/`plaintextHash` pair recorded per chunk in `TelegramChunk` at upload time, but worth being precise: in zero-knowledge mode the server just trusts the client-sent hash (`storedHash = hash`, no independent re-verification against the actual bytes it received) — that field is really there for resumability/bookkeeping, not as the integrity backstop. The actual tamper-detection guarantee is GCM's auth tag, checked at decrypt time.

### Q: What would happen if the same nonce were ever reused with the same key?

This is the one real catastrophic failure mode for GCM, so it's worth being precise about why the code avoids it. GCM's confidentiality guarantee depends on the (key, nonce) pair never repeating: internally it XORs plaintext with a keystream derived from encrypting the nonce, so two ciphertexts produced under the same key+nonce leak the XOR of their two plaintexts to anyone who captures both — and a repeated nonce also breaks GCM's authentication property (an attacker who can observe two messages under the same nonce can, with realistic effort, forge valid ciphertexts for other messages). This codebase avoids it by generating a **fresh random 12-byte nonce per chunk, every time** — `encryptChunk` in `hooks/useFileEncryption.ts` does `crypto.getRandomValues(new Uint8Array(NONCE_SIZE))` unless one is explicitly passed in (which itself only happens for the intentional re-wrap use case, where you're re-deriving under a *different* key, not re-encrypting under the same one). With a 96-bit random nonce, accidental collision probability for any realistic number of chunks a single account would ever upload is vanishingly small (birthday-bound math puts you well north of 2^40 chunks before collision risk becomes non-negligible) — this is standard practice for random-nonce GCM and the reason the nonce size is 12 bytes rather than something smaller.

### Q: What's the actual blast radius if a user's DEK, or their recovery code, leaks?

It's total, and it's worth stating plainly rather than softening it: because the DEK is one stable key for the *entire account* (not per-file, not per-session), anyone who obtains it in cleartext — or obtains the recovery code and the (non-secret) wrapped blob/salt that's already sitting in the `User` document — can decrypt every zero-knowledge-mode file that account has ever uploaded, past and future, for as long as that DEK stays in use. There's no per-file or per-session compartmentalization to limit the damage once that one secret is out. This is the direct cost of the design choice that makes cross-device/cross-file access simple (see the earlier question on why the account-wide DEK replaced per-file keys) — the mitigations available are entirely about *keeping that one secret from leaking* (never transmitted except once, wrapped, over TLS; cached only in IndexedDB, never `localStorage`; held in JS memory as a non-extractable `CryptoKey` via `crypto.subtle.importKey(..., false, ...)`) rather than about limiting what a leak exposes.

### Q: If you were reviewing this for a real gap, what would you flag?

Nothing cryptographically binds a chunk's ciphertext to the specific file and index it's supposed to belong to. `TelegramChunk`'s only integrity guarantee at the database layer is a unique index on `{fileId, chunkIndex}` (`adapters/database/models/TelegramChunk.ts`) — a purely relational constraint. AES-GCM's `encrypt`/`decrypt` calls in this codebase never pass **additional authenticated data** (AAD) — `crypto.subtle.encrypt({name: "AES-GCM", iv, tagLength}, key, plaintext)` has no `additionalData` field set, and neither does the Node equivalent. That means if a chunk row's `fileId` or `chunkIndex` were ever mutated — a migration bug, a bad manual DB edit, or some future code path that moves chunks between file/version records — the ciphertext would still decrypt and authenticate *successfully* under the account's DEK, because GCM's tag only vouches for "this ciphertext, this nonce, this key," not "this ciphertext belongs to this specific file." The fix would be binding `fileId`/`chunkIndex`/`versionId` into GCM's AAD at encrypt time and requiring it again at decrypt time, so a chunk silently relinked to the wrong file's record would fail the auth check instead of decrypting into whatever bytes it actually holds. Given the current scale and threat model (this only matters if something *else* has already gone wrong at the DB layer), it's a real but second-order gap, not an active exploit path.

## Pause / Resume

### Q: What's supposed to happen when you click Pause on an in-progress upload?

Two things, and the "why two" matters: (1) a per-id flag (`pausedIds` in `hooks/useUpload.ts`, `pauseRef` in `hooks/useResume.ts`) tells every worker in the pool "stop claiming new chunks," and (2) — as of this session's fix — the shared `AbortController` for that upload is actually aborted, tearing down whatever chunk request(s) are currently in flight. Only the first half existed originally.

### Q: Why wasn't the abort there from the start? What was the original reasoning?

Deliberately graceful: an in-flight chunk request has already sent its bytes and Telegram is doing real work on it server-side, so the original design let it finish naturally rather than severing the connection mid-transfer, on the theory that killing it "for no benefit" would waste that work. That's a defensible instinct in isolation — but it assumed chunk sends were fast. In this environment they measured 10 to 100+ seconds per chunk (see the concurrency section), so "let it finish naturally" meant Pause could take up to nearly two minutes to actually land, with no feedback and, originally, no button to do anything in the meantime. The fix keeps the correctness benefit (nothing server-side gets corrupted) while abandoning the "don't waste in-flight bytes" assumption, because the *actual* cost of aborting turned out to be small and bounded: an aborted chunk was never committed (`TelegramChunk.create()` only runs after a full, successful response), so it's simply re-sent — at most `CHUNK_CONCURRENCY` chunks' worth of wasted bandwidth, not the whole file, and nowhere near as costly as a two-minute-unresponsive Pause button.

### Q: What was the actual bug — the "zombie worker" issue — before any of this session's fixes?

Resume cleared the *same* pause flag that in-flight-from-before-pause workers were still checking, without first confirming those old workers had actually stopped. Since old workers only re-check the flag at the top of their loop (after whatever chunk they were mid-sending finishes — which, per the timing above, could be up to ~100 seconds later), clicking Resume promptly cleared the flag *while those old workers were still out there mid-flight*. The moment their current chunk finished, they'd loop back, see the flag now false, and keep going — grabbing more chunks from their own independent counter, completely unaware that a second, brand-new worker batch (with its own fresh counter and its own snapshot of "already uploaded" indices) had also just started. Two unsynchronized batches then hit the same file's chunk endpoint concurrently: duplicate chunk sends, contention against Telegram's rate limit, and — once the file was later cancelled by the user — 404s and "message not found" cleanup failures from the zombie batch's stragglers arriving after the file record was already gone.

### Q: How did you actually fix that race, mechanically?

Tracked the in-flight worker-pool call itself, not just a boolean flag. A `Map<id, Promise>` (`activeUploadRun` / `activeResumeRun`) holds whichever `uploadChunks()`/`resumeTelegramUpload()` call is currently running for a given upload id, set the moment that call starts. Resume now does `const priorRun = activeUploadRun.current.get(id); if (priorRun) await priorRun.catch(() => {});` as the *very first thing it does* — before clearing the pause flag or fetching fresh resume info — guaranteeing the previous batch has fully settled (all its workers actually returned) before a new counter and a new "already uploaded" snapshot are created. A boolean flag alone can't express "and I've confirmed the old work has stopped"; a promise can, because you can `await` it.

### Q: Why guard the pause→paused status transition on `status === "pausing"` instead of just setting it unconditionally once the drain completes?

Because Resume can legitimately be clicked *during* the drain (that's the point of making it clickable immediately, covered below), and if it is, the entry's status has already moved on to `"uploading"` by the time the old drain finishes settling. If `settlePause`'s completion handler just unconditionally wrote `"paused"`, it could stomp a resume that's already underway and visibly flip a row backward from "uploading" to "paused" moments after the user resumed it. Checking `u.status === "pausing"` first means: only finalize to "paused" if nothing else has since claimed this upload — same pattern used elsewhere in this codebase for a state update racing an async gap (the `restoreQueue()` duplicate-key fix earlier this session used the identical idea: check the true, current state inside the update itself, not a value captured before the async work started).

### Q: Why introduce a `"pausing"` status at all instead of just showing "Paused" immediately?

Because showing "Paused" instantly was itself a bug, just a quieter one: real chunk uploads kept running in the background for up to that ~100-second window while the UI already claimed nothing was happening. `"pausing"` is the honest label for that gap — draining is still real, ongoing network activity, not idle. Once the abort fix (above) landed, that gap shrank from "however long the slowest chunk takes" to "however long it takes an aborted fetch to actually reject" (well under a second in practice) — but the state still exists because there's always *some* async gap between requesting a stop and confirming it, and collapsing that into an instant, inaccurate "Paused" is exactly the failure this was fixing.

### Q: Why is Resume clickable during `"pausing"`, not just once it reaches `"paused"`?

Because `resumeSingleUpload`/`handleResume` already correctly wait on `activeUploadRun`/`activeResumeRun` for the prior batch before doing anything — that safety doesn't depend on what label the UI happens to be showing. Originally the Resume button was gated on `status === "paused"` only, which meant: if the abort fix's drain window was even a second or two, the user had *nothing clickable* and no way to tell whether the app had frozen — the exact "is it still in progress or not" complaint that started this whole investigation. Since clicking Resume mid-"pausing" is provably safe (it just queues behind the same drain the pause button already triggered), there was no correctness reason to hide it — only a UI decision that turned out to actively make the perceived bug worse.

### Q: How would you test a fix like this?

Honestly — not well with a conventional unit test, and I didn't add one for the race itself. It's a timing-dependent interaction between two async worker pools and real (or realistically mocked) network calls; a fake-timer harness that reliably reproduces "old batch's fetch is still pending when resume fires" would be more fragile and harder to trust than the fix's actual logic is complex. What I *did* verify programmatically was the surrounding contract — full `tsc`/`eslint`/the existing vitest suite stayed green throughout each change — and verified the race itself by reasoning through the exact interleaving (which promise settles when, which flag is read where) rather than by executing it under a scheduler I fully controlled. The honest answer in an interview is: some races are better caught by careful code-level reasoning and manual reproduction than by a test that mostly proves your assumptions about timing, not the code's.

### Q: What's a related bug you noticed but deliberately didn't fix?

`hooks/useResume.ts`'s `cancelRef`/`pauseRef`/`abortRef` are single refs on the hook instance, not keyed per file. If two different pending files were resumed at the same time, they'd share — and stomp on — the same control refs; pausing one could inadvertently affect the other, and the second resume's fresh `AbortController` would silently orphan the first's. That's a real, separate concurrency gap from the one fixed this session (which was about *one* file's pause-then-resume sequence), and fixing it properly would mean re-keying that hook's internal state per fileId — a larger change than the reported bug called for, so it's flagged rather than folded in.

## Sharing & Link Revocation

### Q: How many distinct sharing systems actually exist, and which ones are actually live?

Three models exist in the codebase, but only two are actually wired up. **`FileShare`** (`server/services/shareService.ts`) is a simple, single-file public link. **`ShareLink`** (`server/services/permissionService.ts`) is the real folder-sharing system — token-based public links anchored at a folder, with password protection, use limits, and inheritance to descendant folders. **`FolderShare`** (`adapters/database/models/Foldershare.ts`) is dead code — confirmed by grepping the whole repo for imports of it: nothing outside its own file and a re-export in `models/index.ts` ever references it. It looks like an earlier folder-sharing design that `ShareLink` + `permissionService.ts` superseded, left in place rather than deleted. There's also a third, unrelated mechanism — direct per-user `Permission`/`FolderPermission` grants (share with a specific logged-in user, no public link at all) — which isn't "revocation of a link" in the sense this section is about, but shares the same underlying `resolveFolderPermission` resolution path.

### Q: Walk me through what happens end-to-end when someone creates a folder share link.

`components/dialogs/ShareDialog.tsx` collects a role (viewer/editor), an expiry in days (a real `<input type="number" max={30}>`, not just a display value), and an optional password, then POSTs to `/api/folders/[id]/share` with `{type: "link", role, expiresInDays, password, maxUses}`. The route requires an authenticated owner (`getAuthUser()` + `requireFolderRole(actorId, folderId, "owner")` inside the service call) and wraps the actual creation in `withIdempotency("folder-share-link", idempotencyKey, ...)` before calling `createShareLink`, which clamps `expiresInDays` to `[1, 30]`, generates a 32-byte random token (`crypto.randomBytes(32).toString("hex")`), stores only `sha256(token)` as `tokenHash`, hashes any password with bcrypt, and returns the raw token to the caller exactly once — it's never persisted or logged anywhere, only its hash is.

### Q: Why wrap link creation in an idempotency check (`withIdempotency`) instead of just letting `createShareLink` run directly?

Because creating a share link is a side-effecting POST that a flaky network or an impatient double-click can trigger twice, and "two share links for the same folder" isn't a no-op the way a duplicate GET would be — it mints a second live credential nobody asked for. `withIdempotency` (`server/lib/idempotency.ts`) makes a second call with the *same* `Idempotency-Key` header return the first call's stored result (a completed doc keyed by `{scope, key}`) instead of re-running `fn()` — a concurrent duplicate creates a second `IdempotencyKey` insert, hits the collection's unique-key constraint (`11000`), and gets told "already in progress" (409) rather than racing a second `ShareLink.create()` into existence. This is the same idempotency-key pattern used elsewhere for payment-like operations; it's applied here specifically because the operation being protected mints a durable, usable secret as a side effect.

### Q: Does the "up to 30 days" cap actually mean anything, or could a malicious client bypass it by calling the API directly with a huge number?

It's enforced server-side, not just in the UI's `max={30}` attribute — `createShareLink`'s own code does `Math.min(Math.max(Number(opts.expiresInDays) || 7, 1), 30)` regardless of what the request body says, so a client crafting a raw `POST` with `expiresInDays: 99999` still gets clamped to 30. The UI attribute is purely a UX nicety; the actual boundary is enforced exactly once, in the one service function every creation path (including `updateShareLink`) funnels through.

### Q: How is expiry actually enforced when someone opens a share link — is it checked once, cached, or re-checked every time?

Re-checked on *every single request that touches the shared resource*, with no caching of "this link was valid a moment ago." `resolveShareLink()`'s query is `ShareLink.findOne({ tokenHash, revokedAt: null, expiresAt: { $gt: new Date() } })` — if the current time has passed `expiresAt`, or `revokedAt` has been set, this simply returns nothing and the caller gets a generic 404. Crucially, every action inside a shared folder — browsing (`browseSharedFolder`), creating a subfolder, uploading a file, downloading a file (all in `server/services/sharedFolderService.ts`) — independently calls `resolveShareLinkForFolder` → `resolveShareLink` from scratch. There's no "already validated this session, skip the check" shortcut anywhere in that chain (the password-skip via `sessionVerified` is the one exception, and it only skips the *password* sub-check, not the expiry/revocation query itself — see below). That means if an owner revokes a link while someone is actively browsing it, the very next click — not the next page load, the next *action* — gets rejected.

### Q: There's also a MongoDB TTL index (`expireAfterSeconds: 0`) on `expiresAt`. Doesn't that already handle expiry — why also check it explicitly in application code?

Because the TTL index and the application-level check solve different problems, and only one of them is trustworthy for security. MongoDB's TTL monitor is a background sweep that runs on its own interval (roughly once a minute, not instantly, and not synchronized with any particular request) — by the time it gets around to deleting an expired `ShareLink` document, that document could still sit in the collection, technically queryable, for up to that whole window. If the code relied on "the document doesn't exist" as its only expiry signal, there'd be a real gap where an expired-but-not-yet-reaped link still works. The explicit `expiresAt: { $gt: new Date() }` filter in every read closes that gap completely — it's evaluated against the *current* clock on *this* request, so there's no lag at all. The model's own comment states this design decision directly: the TTL index is "for storage hygiene," not correctness — it exists purely so expired links don't accumulate forever in the collection, and the app would behave identically (just with a slowly-growing table of dead rows) if the TTL index were removed entirely.

### Q: Why does revoking a `ShareLink` set a `revokedAt` timestamp instead of just deleting the document — but revoking a `FileShare` (`revokeFileShares`) does a real `deleteMany`?

This is a genuine inconsistency between the two sharing systems, not a deliberate unified design — worth naming as such rather than rationalizing it as intentional. `ShareLink`'s soft-revoke (`revokeShareLink` → `ShareLink.updateMany(filter, { $set: { revokedAt: new Date() } })`) preserves the row: `listFolderAccess` can still show a revoked link's history (`useCount`, `lastAccessedAt`) to the folder owner, and revoking is naturally idempotent — revoking an already-revoked link is just setting a field to the same kind of value again, not an error. `FileShare`'s hard-delete throws that information away — once revoked, there's no record a share ever existed for that file. If asked "which is more correct," soft-revoke is the better pattern for anything with an owner-facing audit/history view (which `ShareLink` has and `FileShare` doesn't) — the inconsistency likely just reflects `FileShare` being the older, simpler system that predates the richer `ShareLink` design, the same "left in place rather than migrated" pattern that produced the still-supported legacy per-file `encryptionKey` mode.

### Q: What other conditions can make a share link stop working, besides time-based expiry and manual revocation?

A `maxUses` cap, checked in the same `resolveShareLink` call: `if (link.maxUses && link.useCount >= link.maxUses) throw new ServiceError("This link has reached its use limit", 403)`. Unlike expiry/revocation (checked *before* anything else runs, as a hard existence filter in the initial `findOne`), the use-limit check happens *after* the password gate, and successful resolution increments `useCount` via `$inc` in the same update that stamps `lastAccessedAt` — so "uses" specifically means successful, fully-authorized resolutions, not raw hits on the URL (a wrong password or a locked-out attempt doesn't burn a use). There's also the deleted-folder case: `resolveShareLink` checks the link's own record, but `resolveShareLinkForFolder`'s caller-facing services (`browseSharedFolder` etc.) also re-verify the target folder still exists and hasn't been soft-deleted — moving the shared folder to the recycle bin revokes every outstanding link to it just as surely as an explicit revoke would, for the same reason `FileShare`'s file-lookup excludes `deleted: true` files.

### Q: A password-protected link's session is a 2-hour signed cookie (`server/lib/shareSession.ts`) that lets you skip re-entering the password. Could that cookie let someone keep accessing a link after it's revoked or past its own `expiresAt`, since the password check is being skipped?

No — and the reason is the order the checks happen in, not anything special about the cookie. `resolveShareLink`'s very first step, before the `sessionVerified` branch is even reached, is `ShareLink.findOne({ tokenHash, revokedAt: null, expiresAt: { $gt: new Date() } })`. If the link is revoked or expired, that query returns nothing and the function throws immediately — `opts?.sessionVerified` is never even consulted. The session cookie only ever short-circuits the *password* prompt (`if (link.passwordHash && !opts?.sessionVerified) { ...check password... }`); it carries no authority over expiry or revocation, which are existence-level filters applied unconditionally on every call. The cookie itself is also scoped narrowly enough to limit its own blast radius: it's an HttpOnly JWT holding only `sha256(shareToken)` (so it can't be replayed against a different link), signed with the app's own secret, capped at a flat 2-hour `SESSION_TTL` regardless of the link's own `expiresAt` — so even a link created with the maximum 30-day expiry only ever grants a fresh 2-hour password-free window per verification, not a long-lived bypass.

### Q: Why store only `sha256(token)` (`tokenHash`) rather than the raw token itself?

Same reasoning already applied elsewhere in this codebase to `access_token`/`refresh_token` handling — a share token is a bearer credential (256 bits of randomness, "possession of the string is authorization," no separate password required unless the owner added one), so it deserves the same treatment as a session token, not the weaker treatment a lookup-only identifier would get. If the raw token were stored in a `shareUrl`-adjacent field and a database backup, replica, or an admin running an ad hoc query ever leaked a row, every link in that dump would be immediately usable by whoever read it. Hashing means a DB read alone is never sufficient — the model's own comment states the design goal directly: "a DB read (backup, replica lag, admin query) can never leak a usable token." Resolution still works in one step because lookups hash the incoming token and compare (`hashToken(token)` then `findOne({tokenHash})`), so there's no usability cost to doing this.

### Q: The password gate has its own separate brute-force lockout (`failedPasswordAttempts`/`lockedUntil`, 5 attempts → 15-minute lock) distinct from the token itself. Why bother, if the token already has to be guessed correctly first just to reach the password prompt?

Because the token and the password defend against different attackers with different amounts of information. The token (256 bits, delivered out-of-band — e.g. pasted into a chat) is what's actually unguessable; nobody is brute-forcing that over the network. The password is a second factor added *on top of* an already-known-valid token — meant for a scenario like "the link itself leaked or was shared more widely than intended, but the password wasn't" — and passwords, being human-chosen, are frequently far weaker than 256 bits. Once someone has a valid token (which by definition means they can reach the password-check code path at all), the password becomes the only remaining barrier, and without its own lockout it would be attackable at normal network-request speed. The lockout (`if (link.lockedUntil && link.lockedUntil > new Date()) throw new ServiceError(..., 429)`) rate-limits *that specific link's* password independently of everything else — deliberately narrow in scope (this link only, not the token, not the account) matching how narrow the thing it's protecting against actually is.

### Q: A link is created on a parent folder — how does it correctly grant access to a subfolder several levels down without a separate grant existing for each descendant?

`resolveShareLinkForFolder(token, targetFolderId, ...)` first resolves the link normally (`resolveShareLink`, giving back the folder it was actually created on), and if the caller is asking about a *different* folder, it fetches that target folder's materialized `ancestors` array (`Folder.findOne({_id: targetFolderId}, {ancestors: 1})`) and checks whether the link's own folder appears in that chain (`chain.includes(base.folderId)`). If it does, access is granted, scoped to the requested subfolder; if not — including a caller trying to pass a folder that's an *ancestor* of the link's root, or an unrelated folder entirely — it throws a 403. This is the same `ancestors`-array-based O(depth) resolution pattern already used for logged-in-user folder permissions (`resolveFolderPermission`), reused here so a link shared on "Work" transparently covers "Work/Reports" without a second database row ever being created for the subfolder, and without trusting the caller's claim about the relationship — it's independently re-derived every time from the folder's own stored ancestry.

### Q: If you were asked "what would you clean up here," what's the honest answer?

Two concrete things surfaced just from tracing this feature. First, delete `adapters/database/models/Foldershare.ts` (and its re-export in `models/index.ts`) — it's genuinely dead, and leaving a same-purpose, differently-shaped model sitting next to the real one (`ShareLink`) is exactly the kind of thing that causes a future contributor to guess wrong about which one to extend. Second, reconcile the revoke-semantics split between `FileShare` (hard delete, no audit trail) and `ShareLink` (soft-revoke via `revokedAt`, full history preserved) — not necessarily by picking one over the other, but by making the choice deliberate rather than an artifact of `FileShare` predating the richer design. A secondary, smaller one: `FileShare` has no owner-facing "list my active file shares" endpoint the way `listFolderAccess` exists for folders, so a user has no way to audit which files they've shared or revoke one without already knowing its `fileId` — a real, if minor, feature gap rather than a security problem, since `revokeFileShares` already takes `fileId` and would work fine once such a view existed.
